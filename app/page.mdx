# Keploy Quickstart: Echo + Postgres

**Keploy** is an open-source testing tool that automatically generates test cases by recording your API traffic — no manual test writing required. This tutorial walks you through setting it up with a Go app using the **Echo** web framework and **PostgreSQL**.

By the end, you'll have real integration tests generated from live traffic, running entirely from your terminal.

---

## Prerequisites

Before you start, make sure you have the following installed:

- [Go](https://go.dev/dl/) (v1.21 or later)
- [Docker](https://docs.docker.com/get-docker/) and Docker Compose
- [Git](https://git-scm.com/)

<Callout type="tip" title="Linux or macOS recommended">
  Keploy's eBPF-based traffic capture works natively on Linux and macOS. On
  Windows, use **WSL 2** with a Linux distro — the steps below are for a Linux
  environment.
</Callout>

---

## Step 1 — Install Keploy

Run the one-line installer:

```bash
curl --silent -O -L https://keploy.io/install.sh && source install.sh
```

Verify it worked:

```bash
keploy --version
```

You should see something like `keploy v2.x.x`. If the command isn't found, restart your terminal.

## Step 3 — Clean Up Previous Containers (if needed)

If you've run Keploy before, clean up any leftover containers to avoid naming conflicts:

```bash
docker compose down -v
```

This removes all containers and volumes associated with the compose setup.

## Step 4 — Record Test Cases

This is the core Keploy workflow. Instead of writing tests by hand, you **record them from real traffic**.

Start the app and Postgres under Keploy's recorder using Docker Compose:

```bash
keploy record -c "docker compose up" --container-name "echoApp" --build-delay 50
```

**Key flags:**

- `--container-name "echoApp"` — specifies the container name to record
- `--build-delay 50` — waits 50 seconds for the app to start (increase if needed)

Keploy boots your app via Docker Compose, intercepts all network calls (HTTP in, Postgres out), and saves them as test cases. Watch the logs until you see:

```
⇨ http server started on [::]:50732
```

Now, in a **second terminal**, fire a few real requests:

**Create a URL entry - Example 1:**

```bash
curl --request POST \
  --url http://localhost:8082/url \
  --header 'content-type: application/json' \
  --data '{
  "url": "https://www.linkedin.com/in/burninghoax"
}'
```

Response:

```json
{ "ts": 1773843729330422855, "url": "http://localhost:8082/BRo9mtSH" }
```

**Create a URL entry - Example 2:**

```bash
curl --request POST \
  --url http://localhost:8082/url \
  --header 'content-type: application/json' \
  --data '{
  "url": "https://google.com"
}'
```

Response:

```json
{ "ts": 1773843736646358824, "url": "http://localhost:8082/Lhr4BWAi" }
```

**Fetch all entries:**

```bash
curl http://localhost:8082/url
```

**Fetch a specific entry:**

```bash
curl http://localhost:8082/BRo9mtSH
```

Stop the recorder with `Ctrl+C` when done.

<Callout type="tip" title="What just got saved?">
  Keploy wrote YAML files under `./keploy/` — one per request. Each file
  captures the full HTTP exchange plus every Postgres query made during that
  request, stored as mocks.
</Callout>

## Step 5 — Run the Tests

Replay everything Keploy recorded using the same Docker Compose approach:

```bash
keploy test -c "docker compose up" --container-name "echoApp" --build-delay 50
```

Keploy will:

1. Start your app
2. Replay each recorded HTTP request
3. Intercept outgoing Postgres calls and return the saved mocks
4. Compare the live response against the recorded one

## Step 6 — (Optional) Inspect the Test Files

Keploy organizes tests in sets. View a recorded test:

```bash
cat keploy/test-set-2/tests/test-1.yaml
```

You'll see the full picture — request headers, body, status code, and every Postgres query mocked out. Test sets are created under `./keploy/` with this structure:

```
keploy/
├── test-set-0/
│   ├── tests/
│   │   └── test-1.yaml
│   └── mocks.yaml
├── test-set-1/
│   └── mocks.yaml
└── test-set-2/
    ├── tests/
    │   ├── test-1.yaml
    │   ├── test-2.yaml
    │   └── ...
    └── mocks.yaml
```

These files are human-readable and version-controlled, so they travel with your codebase.

<Callout type="warning" title="Don't commit secrets">
  If your app passes API keys or tokens in headers, review the YAMLs before
  committing. Keploy captures headers verbatim.
</Callout>

---

## Why This Matters

Traditional integration tests require you to:

- Write fixture data
- Mock your database manually
- Update mocks every time a query changes

Keploy inverts this: **use your app once, get the tests for free.** The mocks come from real Postgres behavior, not hand-written stubs, so they actually reflect what your code does.
